# teletext-server: architecture

The design of the server's behaviour is `~/devel/neoteletext-common/PROTOCOL.html`, shared with the engine and the browser. This document holds the owner's decisions for this repository (section 2), how the server runs where it runs (section 3), and what is built (section 5).

## 1. What it is

The NeoTeletext server is a teletext application server: applications publish pages and streams, and each client receives, as 42-byte teletext packets, only what changed in the pages it shows. It imports its teletext from `neoteletext-renderer-teletext` at one pinned commit and writes here, once, what the engine lacks for a server.

## 3. How the server runs where it runs

### 3.1 The runtime and its hosts

The owner asked for async Rust that runs on several desktop and server systems, on Cloudflare, and in WebAssembly. Those three pull against each other:
- **Native:** tokio, many threads, processes and files.
- **Cloudflare Workers:** `wasm32-unknown-unknown`, one thread, no tokio, futures that are not `Send`, no processes, and an object evicted when idle (hibernation).
- **WebAssembly generally:** no threads and no clock unless the host gives them.

Code written against one async runtime does not run on the others.

**The answer is to keep the async out of the runtime.** `teletext-runtime` is a state machine, one per channel:

```
host → runtime:  Opened(connection, cookies) | Frame(connection, bytes) | Closed(connection)
                 FromApplication(application, message) | Deadline(now) | Loaded(key, bytes)
runtime → host:  Send(connection, bytes) | Close(connection, reason)
                 ToApplication(application, message) | WakeAt(time) | Load(key) | Store(key, bytes)
```

Each host is a short async loop: wait for whatever comes next (a socket, an application, a timer), give it to the runtime with the time, and carry out the effects. The engine's own web agent works this way (`neoteletext-web`, sans I/O).

| | A synchronous runtime driven by async hosts (chosen) | An async runtime generic over a host trait |
|---|---|---|
| Native, Cloudflare, WebAssembly | One code, three short hosts | One code, if every future avoids `Send` and every executor's quirks |
| Tests | Deterministic: the test sets the time and feeds events; no network | Need an executor and fake I/O |
| Hibernation on Cloudflare | Natural: the state is plain data, saved and reloaded | Awaits in flight are lost when the object is evicted |
| Timers | One "wake me at" effect, which is exactly a Durable Object's single alarm | One timer per task, which Cloudflare does not have |
| Cost | Event and effect types to define; a host loop each | Less code at first |

### 3.2 The native host

- **Async runtime:** tokio, one task per channel holding that channel's runtime. A channel is single-threaded, as the design asks; channels run in parallel.
- **HTTP and WebSocket:** `hyper` serves the engine's channel layout (DOC-1779) with `ETag`, and performs the WebSocket upgrade with the engine's `ws::accept_for`. The server-side WebSocket framing is this repository's own code, sans I/O, as planned.
- **The listening socket:** the one systemd passes, when it passes one (socket activation, requirement 5.6, DEC-1767), so a restart refuses no connections; otherwise the address `--listen` names, bound by the server.
- **TLS:** `rustls`, with certificates from files. A proxy such as Caddy may front it instead.
- **Applications:** child processes over stdio, programs of their own over a Unix domain socket, or programs anywhere, on another machine too, over a WebSocket with the channel's secret (decision 17, REQ-1044).
- **What survives a restart:** the state directory (`--state`, or systemd's `StateDirectory=`): each channel's kept pages and declarations, the session cookie's keys, the accumulated figures (decisions 17 and 19). On `SIGTERM` every viewer is sent a Close with 4100, try again (DOC-1919), and what is kept is written.
- **Log and figures:** structured events through `tracing` on standard error (decision 18); `/metrics`, `/healthz` and `/readyz` on the administration listener (decision 19).
- **Builds:** one binary each for Linux, macOS and Windows, on x86-64 and arm64 (REQ-1020), with no library of its own beside it: the server links no C code and no TLS library. Static as far as each system allows, found on 3 November 2026 (TODO-2055):
  - **Linux:** static only on the musl target (`x86_64-unknown-linux-musl`, a static PIE, which `deploy/ionos/deploy.sh` builds); the default GNU target links the C library dynamically.
  - **macOS:** links the system's `libSystem` and `libiconv` dynamically, both part of every macOS, since Apple supports no static executable.
  - **Windows:** links the system's DLLs (`kernel32`, `ws2_32`, `ntdll`, `bcryptprimitives`, `userenv`). The MSVC target, by Rust's default for it, also needs the Visual C++ runtime DLL unless built with `-C target-feature=+crt-static`; the GNU target uses the system's `msvcrt.dll`.
  - Where each has been built and tested, and how, is REQ-1020's State.
  - **What Windows lacks:** a channel's program cannot be a Unix domain socket there, only a command (DEC-2433); and the server makes no session cookie key, since its one source of random bytes is `/dev/urandom` (`state::random_key`), so on Windows a session does not continue across connections and nothing secret is written to the state folder. TODO-2055 holds the owner's choice that would change that.
- **The channels file:** the native server reads one JSON file, `--channels`, naming each channel's folder, its name, and one of three ways its program reaches it (decision 17):
  - `command`, the command that runs its program, with `directory`, the directory to run it in: the server starts it and speaks to it over its standard input and output;
  - `socket`, on Linux and macOS only, the Unix domain socket of a program that runs as a service of its own; on Windows a channel with a socket is refused at start (DEC-2433);
  - `secret_variable` or `secret_file`, the environment variable or the file that holds the channel's secret, for a program that connects over a WebSocket from anywhere, on every system (REQ-1044). The secret is never written in the channels file itself; a file's surrounding white space is not part of it, and a file over 4,096 bytes, an empty secret or a variable not set stops the server at start. The program connects to `<channel>program` with `Authorization: Bearer <secret>`, compared in constant time, as on the Cloudflare host (section 3.3, REQ-1024), whose route and check are the runtime's (`landing::Route::Program`, `landing::program_admitted`). A request without the secret is answered 401 before anything else of it is looked at, a second program while one is connected 409, and a channel with another kind of program 404. Each text message is one line of the program protocol, at most `LONGEST_LINE`, the bound of the other transports; the server sends each line as one text message without its newline. Once in, the program is served exactly as one on a Unix domain socket: it is sent `start`, then `connected` for each open connection, and when it goes its channel is told it ended and the next program may connect. A quiet program's connection is pinged as a viewer's is, and dropped when nothing comes back, so that a program whose machine vanished does not keep the next one out. Over plain HTTP the secret crosses the network in the clear: a deployment puts TLS in front (Caddy terminates `https` and `wss`), and a program elsewhere connects with `wss://`.

  An entry may also name `initial_page`, three decimal digits such as `"302"`, the page its viewers start on and `channel.ttx` reports; without one it is 100. It may name `default_rules`, `"none"` or `"send_all"`, which says what a page has for a connection its program gave no rule table (neoteletext-common's `docs/page-rules.md` RULE-53, REQ-6532): with `"none"`, the default when it is left out, the page has no table and so sends its channel no input (REQ-6523); with `"send_all"` it has the default table, the engine's `default_send_all`, which sends every kind of input as push protocol 8 did. `wheel`, true or false, adds the default table's `wheel` rule and does nothing else: `channel.ttx` no longer says anything of input, since push protocol 9 withdrew `push.input` and `push.wheel` and push protocol 10 keeps them withdrawn (RULE-49). A folder is letters, digits, `-` and `_`; a relative `directory`, `socket` or `secret_file` is taken from the file's own folder, so `../<repository>` names a channel's repository beside the channels'. NeoTeletext's own file is `channels.json` in `~/devel/neoteletext-server-channels`, which `scripts/deploy.sh` reads as its manifest:

  ```json
  {"channels":[
    {"folder":"hackaday","name":"Hackaday","command":["node","--disable-warning=ExperimentalWarning","src/main.ts"],"directory":"../neoteletext-server-channel-hackaday"},
    {"folder":"oldhackaday","name":"Hackaday (old)","command":["uv","run","--frozen","--no-dev","python","-m","hackaday"],"directory":"hackaday"},
    {"folder":"radio","name":"Radio","socket":"sockets/radio.sock"},
    {"folder":"remote","name":"Remote","secret_file":"/etc/neoteletext/remote.secret"}
  ]}
  ```

  What the server and a program say to each other over any of the three transports is the program protocol, DOC-1964 to DOC-1978 of `neoteletext-common/PROTOCOL.html`.

### 3.3 The Cloudflare host

`workers-rs` (0.8.7, 25 September 2026) has what the server needs:
- Durable Objects;
- hibernatable WebSockets: `State::accept_web_socket`, `accept_websocket_with_tags`, `get_websockets`, and the `websocket_message`, `websocket_close` and `websocket_error` handlers;
- alarms;
- SQLite storage.

Its `DurableObject` trait's async handlers do not need `Send`.

- **One Durable Object per channel** is the design's single actor per channel, with Cloudflare's routing to it: every connection to a channel reaches the same object, which TODO-2023 item 3 asks of a native deployment too.
- **Hibernation:** an idle channel's object is evicted while its WebSockets stay open.
  - What must survive goes to the object's SQLite storage through the runtime's `Store` effects: published pages, sessions, each connection's tuned pages.
  - Each connection's last-sent versions are lost, so after a wake every tuned page goes whole once (DOC-1949), about 1 KB a page.
  - A live channel keeps its object awake, and is billed for it.
- **Channels:** the variable `CHANNELS` in `wrangler.toml` lists the channels served, each `{"folder","name","wheel","default_rules"}`, the last two read as the native host reads them from its channels file (RULE-53): `wheel` false and `default_rules` `"none"` when left out, and any other value a fault of the configuration that stops the channel's object.
- **Static pages** should be served by the Worker itself from the edge's cache or R2, without waking the channel's object; as built (decision 20) the object answers them (an rdm to-do).
- **Applications:** there are no processes. A program runs wherever its owner runs it and opens a WebSocket to its channel's Durable Object over `wss://`, with the channel's secret, so the object stays the server of every connection it holds and can hibernate (decision 17, requirement 1.5).
- **Limits to design within** (Cloudflare's published limits):
  - 128 MB of memory per isolate;
  - 30 seconds of CPU per request by default, up to 5 minutes;
  - the Worker's compressed size, which the dependencies must keep small.
- **Clock and randomness:** the clock comes from the host as every event's time. Random session tokens come from `getrandom`, with the WebAssembly back end Cloudflare needs (a library to approve).

### 3.4 WebAssembly beyond Cloudflare

The runtime and the engine's `core` and `formats` already build for `wasm32-unknown-unknown`. A WASI host (`wasm32-wasip2`), or a runtime in a web page for testing, is a further host if needed; nothing in the runtime changes.

## 4. The engine

Every `neoteletext-*` dependency is a git dependency on the engine's public repository, `https://github.com/neoteletext/neoteletext-renderer-teletext`, at one `rev`, with `default-features = false` and the features named; the check script refuses two revisions. Until 28 October 2026 it was the engine's local repository, `file:///Users/andrewstuart/devel/neoteletext-renderer-teletext`, whose history the gates and deploys copied to the Linux host; the engine went public that day, on the owner's instruction, and the dependency moved to it at the same commit, `e09a589`.

Over a connection limit: WELCOME agreeing SNAPSHOT, DENIED 429 with no place, close.

## 6. Security of pictures

What renderer parity added that reads a program's input or holds memory for it, and what bounds it (`docs/renderer-parity.md` section 19, the threats that are the server's; reviewed 19 November 2026):

| Threat | Mitigation |
|---|---|
| A program fills the server's memory with kept pictures (1) | `MOST_KEPT_STREAM_BYTES` a picture (the engine's `MAX_PICTURE_STREAM_BYTES`), `MOST_KEPT_PICTURES` a channel and `MOST_KEPT_COST` a channel, refused with `kept_over_limit` naming the constant and never evicted (PAR-17; `kept/tests.rs`). The cost counts each stream's bytes, each companion's line, and each reader held at what it holds (`Checker::held_bytes`, TODO-6845): a ReGIS reader as its renderer reports it (`regis::Validator::held_bytes`, the ReGIS renderer's DEC-6850), measured again after every append it takes, about 19 KB new and 20 to 70 KB for the demonstration pages, up to the renderer's `MAX_HELD_BYTES` (22,751,666); a NAPLPS reader as its renderer reports it (`naplps::Validator::held_bytes`, the NAPLPS renderer's DEC-6858; TODO-6860), measured again after every append it takes, with the stroke font and joined sets it is given: 32,600 bytes new or for an ordinary page, 1,650,136 for the heaviest stream known (every DRCS character and texture defined at the largest mask, 719 bytes), never more than the renderer's `MAX_HELD_BYTES` (1,971,344) besides the font and sets. A message after which its picture's reader would pass `MOST_KEPT_COST` with the rest is refused with `kept_over_limit`, and that reader, having read it, is let go.
