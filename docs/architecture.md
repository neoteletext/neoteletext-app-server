# teletext-server: architecture

The design of the server's behaviour is `~/devel/neoteletext-common/PROTOCOL.html`, shared with the engine and the browser. This document holds the owner's decisions for this repository (section 2), how the server runs where it runs (section 3), and what is built (section 5).

## 1. What it is

The NeoTeletext server is a teletext application server: applications publish pages and streams, and each client receives, as 42-byte teletext packets, only what changed in the pages it shows. It imports its teletext from `neoteletext-renderer-teletext` at one pinned commit and writes here, once, what the engine lacks for a server.

## 3. How the server runs where it runs

### 3.1 The runtime and its host

The owner asked for async Rust that runs on several desktop and server systems (DEC-1068). Cloudflare Workers, asked for at the same time, was dropped as a target on 21 November 2026 (DEC-7011); the native host is the only one.

**The async is kept out of the runtime.** `teletext-runtime` is a state machine, one per channel:

```
host → runtime:  Opened(connection, address) | Frame(connection, bytes) | Closed(connection)
                 FromApplication(application, message) | Deadline(now) | Loaded(key, bytes)
runtime → host:  Send(connection, bytes) | Close(connection, reason)
                 ToApplication(application, message) | WakeAt(time) | Load(key) | Store(key, bytes)
```

The host is a short async loop: wait for whatever comes next (a socket, an application, a timer), give it to the runtime with the time, and carry out the effects. The engine's own web agent works this way (`neoteletext-web`, sans I/O).

| | A synchronous runtime driven by an async host (chosen) | An async runtime generic over a host trait |
|---|---|---|
| Tests | Deterministic: the test sets the time and feeds events; no network | Need an executor and fake I/O |
| Timers | One "wake me at" effect | One timer per task |
| Cost | Event and effect types to define; a host loop | Less code at first |

### 3.2 The native host

- **Async runtime:** tokio, one task per channel holding that channel's runtime. A channel is single-threaded, as the design asks; channels run in parallel.
- **HTTP and WebSocket:** `hyper` serves the engine's channel layout (DOC-1779) with `ETag`, and performs the WebSocket upgrade with the engine's `ws::accept_for`. The server-side WebSocket framing is this repository's own code, sans I/O, as planned.
- **The listening socket:** the one systemd passes, when it passes one (socket activation, requirement 5.6, DEC-1767), so a restart refuses no connections; otherwise the address `--listen` names, bound by the server.
- **TLS, HTTP/2 and HTTP/3, served by the server itself** (DEC-6964; REQ-6965, REQ-6966, REQ-6967), when it is started with both of two options:
  - `--tls-certificate FILE`, a certificate chain in PEM, the server's own certificate first;
  - `--tls-key FILE`, that certificate's private key in PEM.

  The files are read at start, before any channel's program is started; a file that cannot be read or holds nothing of its kind, a key that is not the certificate's, or one option without the other stops the server there with a message naming the file. They are read again at `SIGHUP` (REQ-7003; `systemctl reload`, which the IONOS unit's `ExecReload` turns into `SIGHUP`, and which `neoteletext-certificate-sync` runs when Caddy renews the certificate): a pair that loads is used for every TLS and QUIC handshake from then on, connections already made keeping theirs, and one that does not is logged under the target `tls` and the pair in use kept. `--origin` then starts `https://`. With them:
  - **TCP** is TLS 1.3 or 1.2 (`rustls` over the `ring` provider), and by ALPN the client takes `h2` or `http/1.1`. HTTP/2 is hyper's, with extended CONNECT enabled (`SETTINGS_ENABLE_CONNECT_PROTOCOL`, RFC 8441 section 3).
  - **UDP at the same address and port** is QUIC (`quinn`, TLS 1.3, ALPN `h3`, no early data), carrying HTTP/3 through the engine's layer, the crate `neoteletext-http3` (the engine's REQ-6986; built here as `teletext-http3` and moved to the engine, which gave it a client side, on 21 November 2026, TODO-6991): sans I/O and `no_std`, it reads RFC 9114's frames, stream types and SETTINGS and RFC 9204's QPACK field sections from byte slices, with the static table and the Huffman code alone. It tells the peer a dynamic table of no capacity, so a field section that refers to one is the connection error `QPACK_DECOMPRESSION_FAILED`. With systemd's socket activation the TCP listener is the one passed, and the UDP socket is bound by the server at that listener's address, so QUIC connections end at a restart.
  - **Every answer over TCP carries `Alt-Svc: h3=":<port>"`**, which is how a client learns of HTTP/3. The port is the public one, the port viewers reach the server at (REQ-6965 version 2): the port `--origin` names, or its scheme's default when it names none, 443 for `https` (RFC 9110 section 4.2.2). It is never taken from the listening address, which behind a proxy that relays connections is a port no viewer can reach (DEC-6972; found on 20 November 2026 behind caddy-l4, where the server named its own port 9443). With TLS, an `--origin` no port can be read from stops the server at start. QUIC is still served at the listening address and port.
  - **A channel's push and program WebSockets** are opened by an HTTP/1.1 upgrade as before, or by an extended CONNECT whose `:protocol` is `websocket` over HTTP/2 (RFC 8441) or HTTP/3 (RFC 9220). `http::decide` checks all three alike (no `Origin`, the push subprotocol, the program's secret, one program at a time) and an extended CONNECT is answered 200 with `sec-websocket-protocol` and no `Sec-WebSocket-Accept`; any other `:protocol` is answered 501, and a CONNECT to any other route 404. The stream is then served by `connection::serve_halves`, the code that serves an upgraded socket, its bytes RFC 6455 frames unchanged, over HTTP/3 as the payload of DATA frames. So several tabs' WebSockets share one TCP or QUIC connection, and each is still one connection to the channel: one view with one selection (DEC-1527).
  - **The viewer's address** (VS-304) is the TCP or QUIC peer's; `--trusted-proxy` still applies when that peer is the proxy named.
  - **Behind a proxy that relays TLS without ending it** (DEC-6972, REQ-6974): a third option, `--proxy-protocol`, which takes no value and is valid only with `--trusted-proxy ADDRESS` and the two TLS options; given without either, the server stops at start, before any program is started. Such a proxy (caddy-l4 in caddyrouter's Caddy) never sees a request, so it cannot write `X-Forwarded-For`; it puts a PROXY protocol version 2 header (HAProxy Technologies' "The PROXY protocol, Versions 1 & 2", section 2.2) at the start of each TCP connection instead. With the option:
    - every TCP connection must come from the trusted proxy's address and start with that header, read before the TLS handshake, byte for byte to the end its length states and no further; any other connection, and one whose header is refused, cut short or not whole within `PROXY_HEADER_WITHIN`, is closed with nothing sent;
    - a PROXY command over TCP on IPv4 or IPv6 gives the viewer's address, its source, used wherever the peer's was (the bound on new viewers, the snapshot limits); a LOCAL command, the proxy's own connection such as a health check, leaves the proxy's address standing; UDP, Unix sockets, the unspecified family, any version but 2 and the version 1 text header are refused, and TLV vectors are skipped unread;
    - `X-Forwarded-For` is not read on TCP (`http::Source::Viewer`), since it can only be the viewer's own word;
    - QUIC is not changed: a UDP relay carries no such header, and DEC-6972 item 4 leaves HTTP/3 ended at the proxy.

    The reader is `crates/teletext-native/src/proxy_protocol.rs`, without input or output, beside the WebSocket frame reader; `serving.rs` carries the bytes to it. Without the option the server never looks for a header.
  - **At a stop** (REQ-7002): TCP is listened on no more and every new QUIC handshake is refused with `CONNECTION_REFUSED`, so a client goes to the next process; every HTTP/2 connection is sent GOAWAY (hyper's graceful shutdown) and every HTTP/3 connection GOAWAY on the server's control stream, naming the first request it will not process, and later requests on it are reset with `H3_REQUEST_REJECTED`; the channels close their WebSockets with 4100 as before, each HTTP/3 stream's end waiting for the peer to acknowledge it at most `STREAM_ACKNOWLEDGED_WITHIN` (1 s); then every QUIC connection is closed with `H3_NO_ERROR` and the endpoints given at most `QUIC_CLOSED_WITHIN` (1 s) to fall idle. A client that missed the close is reset by the next process at its next packet: the stateless reset key is derived from the handle secret the state directory keeps, and connection IDs are not checked on arrival, so any short packet for an unknown connection is answered with a reset. Without a state directory the key lasts one run.
  - **QUIC's sockets:** a socket a core shares the port (`SO_REUSEPORT`, on Unix), each with an endpoint of its own and one count of connections between them (REQ-7006). The serving log line names `quic_sockets`, the receive buffer the system gave each (`quic_receive_buffer`, asked 8 MiB, had up to `net.core.rmem_max`), and how many datagrams one send and receive carry (`quic_send_segments`, `quic_receive_segments`; 64 and 64 on chunko's Linux 7.0, so quinn's UDP segmentation and receive offload are in use).
  - **Bounds:** every bound on this input is a constant of `crates/teletext-native/src/limits.rs` or of the engine's `neoteletext_http3::limits`, each with its reason, and section 7 lists them. Among them the three on what is open at once: TCP connections `MAX_TCP_CONNECTIONS` (60,000, closed unread past it; a WebSocket upgraded from one keeps its place), TLS handshakes in progress `MAX_TLS_HANDSHAKES` (1,024), and push WebSockets over every version together `MAX_PUSH_WEBSOCKETS` (60,000, 503 past it), which `MAX_QUIC_CONNECTIONS` equals (REQ-7004, REQ-7006).

  Without the two options the server serves plain HTTP/1.1 on TCP exactly as before, for a proxy such as Caddy in front, and makes no UDP socket. NeoTeletext's own deployment stays so, behind caddyrouter (DEC-6964 item 7, REQ-6960). Obtaining certificates (ACME) is not built.
- **Applications:** child processes over stdio, programs of their own over a Unix domain socket, or programs anywhere, on another machine too, over a WebSocket with the channel's secret (decision 17, REQ-1044).
- **What survives a restart:** the state directory (`--state`, or systemd's `StateDirectory=`): each channel's kept pages and declarations, the viewer-handle secret (`viewer-handle.key`, VS-305; it replaced the session cookie's keys, deleted once at start, when DEC-6471 removed cookies and sessions on 18 November 2026), the accumulated figures (decisions 17 and 19). On `SIGTERM` every viewer is sent a Close with 4100, try again (DOC-1919), and what is kept is written.
- **Log and figures:** structured events through `tracing` on standard error (decision 18); `/metrics`, `/healthz` and `/readyz` on the administration listener (decision 19).
- **Builds:** one binary each for Linux, macOS and Windows, on x86-64 and arm64 (REQ-1020), with no library of its own beside it: TLS and QUIC are `rustls` and `quinn` inside the binary, over `ring`, the one library with native code, and no system TLS library is linked. Static as far as each system allows, found on 3 November 2026 (TODO-2055):
  - **Linux:** static only on the musl target (`x86_64-unknown-linux-musl`, a static PIE, which `deploy/ionos/deploy.sh` builds); the default GNU target links the C library dynamically.
  - **macOS:** links the system's `libSystem` and `libiconv` dynamically, both part of every macOS, since Apple supports no static executable.
  - **Windows:** links the system's DLLs (`kernel32`, `ws2_32`, `ntdll`, `bcryptprimitives`, `userenv`). The MSVC target, by Rust's default for it, also needs the Visual C++ runtime DLL unless built with `-C target-feature=+crt-static`; the GNU target uses the system's `msvcrt.dll`.
  - Where each has been built and tested, and how, is REQ-1020's State.
  - **What Windows lacks:** a channel's program cannot be a Unix domain socket there, only a command (DEC-2433); and the viewer-handle secret is written to the state folder without the owner-only permissions it has on Unix (DEC-5248 holds the owner's open choice). *Amended 20 November 2026:* this bullet said the server made no session cookie key on Windows (TODO-2055); the session cookie is gone (DEC-6471), and the secret is made from `ring`'s system random source on every platform.
- **The channels file:** the native server reads one JSON file, `--channels`, naming each channel's folder, its name, and one of three ways its program reaches it (decision 17):
  - `command`, the command that runs its program, with `directory`, the directory to run it in: the server starts it and speaks to it over its standard input and output;
  - `socket`, on Linux and macOS only, the Unix domain socket of a program that runs as a service of its own; on Windows a channel with a socket is refused at start (DEC-2433);
  - `secret_variable` or `secret_file`, the environment variable or the file that holds the channel's secret, for a program that connects over a WebSocket from anywhere, on every system (REQ-1044). The secret is never written in the channels file itself; a file's surrounding white space is not part of it, and a file over 4,096 bytes, an empty secret or a variable not set stops the server at start. The program connects to `<channel>program` with `Authorization: Bearer <secret>`, compared in constant time; the route and the check are the runtime's (`landing::Route::Program`, `landing::program_admitted`). A request without the secret is answered 401 before anything else of it is looked at, a second program while one is connected 409, and a channel with another kind of program 404. Each text message is one line of the program protocol, at most `LONGEST_LINE`, the bound of the other transports; the server sends each line as one text message without its newline. Once in, the program is served exactly as one on a Unix domain socket: it is sent `start`, then `connected` for each open connection, and when it goes its channel is told it ended and the next program may connect. A quiet program's connection is pinged as a viewer's is, and dropped when nothing comes back, so that a program whose machine vanished does not keep the next one out. Over plain HTTP the secret crosses the network in the clear: a deployment serves TLS itself (`--tls-certificate`, `--tls-key`) or puts TLS in front (Caddy terminates `https` and `wss`), and a program elsewhere connects with `wss://`.

  An entry may also name `initial_page`, three decimal digits such as `"302"`, the page its viewers start on and `channel.ttx` reports; without one it is 100. It may name `default_rules`, `"none"` or `"send_all"`, which says what a page has for a connection its program gave no rule table (neoteletext-common's `docs/page-rules.md` RULE-53, REQ-6532): with `"none"`, the default when it is left out, the page has no table and so sends its channel no input (REQ-6523); with `"send_all"` it has the default table, the engine's `default_send_all`, which sends every kind of input as push protocol 8 did. `wheel`, true or false, adds the default table's `wheel` rule and does nothing else: `channel.ttx` no longer says anything of input, since push protocol 9 withdrew `push.input` and `push.wheel` and push protocol 10 keeps them withdrawn (RULE-49). A folder is letters, digits, `-` and `_`; a relative `directory`, `socket` or `secret_file` is taken from the file's own folder, so `../<repository>` names a channel's repository beside the channels'. NeoTeletext's own file is `channels.json` in `~/devel/neoteletext-server-channels`, which `scripts/deploy.sh` reads as its manifest:

  ```json
  {"channels":[
    {"folder":"hackaday","name":"Hackaday","command":["node","--disable-warning=ExperimentalWarning","src/main.ts"],"directory":"../neoteletext-server-channel-hackaday"},
    {"folder":"oldhackaday","name":"Hackaday (old)","command":["uv","run","--frozen","--no-dev","python","-m","hackaday"],"directory":"hackaday"},
    {"folder":"radio","name":"Radio","socket":"sockets/radio.sock"},
    {"folder":"remote","name":"Remote","secret_file":"/etc/neoteletext/remote.secret"}
  ]}
  ```

  What the server and a program say to each other over any of the three transports is the program protocol, DOC-1964 to DOC-1978 of `neoteletext-common/PROTOCOL.html`.

## 4. The engine

Every `neoteletext-*` dependency is a git dependency on the engine's public repository, `https://github.com/neoteletext/neoteletext-renderer-teletext`, at one `rev`, with `default-features = false` and the features named; the check script refuses two revisions. Until 28 October 2026 it was the engine's local repository, `file:///Users/andrewstuart/devel/neoteletext-renderer-teletext`, whose history the gates and deploys copied to the Linux host; the engine went public that day, on the owner's instruction, and the dependency moved to it at the same commit, `e09a589`. It went back to the local repository while later commits were unpublished, and returned to GitHub on 21 November 2026 at `3f02881`, the commit the browser pins. The ReGIS and NAPLPS renderers stay on the `file://` sources the engine itself names them by at that commit, so that the build holds one copy of each; `deploy/ionos/deploy.sh` builds the server on the development machine, where they resolve, and rewrites them to GitHub where it builds `neottx` on the builder.

## 5. What is built

- The repository and its process (decision 3), 25 October 2026.
- `teletext-runtime` (decision 2): a channel as a state machine, with no input or output.
  - It speaks what the browser speaks today: the engine's channel layout, pages as T42 page frames, and the input protocol with WELCOME and cursor records (no input modes since 27 October 2026, DOC-1922).
  - Applications are state machines in the server's process; the `Remote` one stands for a program of its own (decision 8), which every channel now is.
  - Shared pages are published once; a session's own pages go to it alone.
- `teletext-native`: the native host on tokio and hyper.
  - Each channel's runtime runs in a task.
  - Every connection catches up on the shared pages from the change log by itself (decision 7).
  - `teletext-load` measures scale.
  - `scripts/deploy.sh` deploys as a systemd service.
  - Requirement 1.4's measurement: 100,000 connections at 9.5 KB each.

## 7. Security of TLS, HTTP/2 and HTTP/3 served directly

What DEC-6964 added that reads input from the network, and what bounds it (reviewed 20 November 2026, with the build). Served directly, the server's TLS, HTTP/2, QUIC and HTTP/3 readers face any peer on the network, where before only a proxy's HTTP/1.1 reached it. The constants are in `crates/teletext-native/src/limits.rs` unless the engine's `neoteletext_http3::limits` is named; `scripts/check.sh` fails if one is defined twice or elsewhere (REQ-6967).

| Threat | Mitigation |
|---|---|
| A peer opens connections and never finishes a handshake | `HANDSHAKE_WITHIN` (10 s) for TLS on TCP and for QUIC; TCP connections are at most `MAX_TCP_CONNECTIONS` (60,000) and TLS handshakes in progress among them `MAX_TLS_HANDSHAKES` (1,024), a connection past either closed unread (REQ-7004); QUIC connections, handshakes among them, are at most `MAX_QUIC_CONNECTIONS` (60,000), and one more is refused. |
| QUIC used to amplify traffic at a forged address | QUIC's own rule: `quinn` sends at most three times what it received until the address is validated (RFC 9000 section 8.1). No Retry packet is asked for. A stateless reset, sent for any short packet of a connection the endpoint does not know (REQ-7002), is always smaller than that packet (RFC 9000 section 10.3), and at most one goes each `STATELESS_RESET_EVERY` (20 µs). |
| A peer that learns the stateless reset key could reset other viewers' connections | The key is HMAC-SHA-256 under the handle secret (VS-305), which never leaves the state directory, of a label of its own; a token is sent only to the client of its connection, inside the encrypted handshake. Connection IDs are HMAC of a count under a key made at random at each start. |
| A burst of handshakes overflows the QUIC socket | A socket a core shares the port (`SO_REUSEPORT`), each with its own endpoint, and each asks for an 8 MiB receive buffer (`QUIC_RECEIVE_BUFFER_BYTES`), had up to `net.core.rmem_max` (REQ-7006); the serving line says what was had. |
| A request replayed from TLS early data | Early data is off for QUIC (`max_early_data_size` 0) and rustls takes none on TCP by default. |
| One peer opens streams without end | `MAX_CONCURRENT_STREAMS` (100) on an HTTP/2 connection and on a QUIC connection; `MAX_UNIDIRECTIONAL_STREAMS` (8) on a QUIC connection; and push WebSockets over every version together `MAX_PUSH_WEBSOCKETS` (60,000), past which a push request is answered 503 (REQ-7006), so that a hundred streams on each of many connections cannot add up past what the server is built to hold. Streams opened and reset in a flood over HTTP/2 are bounded by hyper's own counts of reset streams, left at their defaults. |
| A request stream opened and left, or a head sent a byte at a time | `H3_HEAD_WITHIN` (10 s) for an HTTP/3 request's head; a QUIC connection idle for `QUIC_IDLE_AFTER` (60 s) is closed; an HTTP/2 connection is pinged after `H2_PING_AFTER` and dropped when no answer comes within `H2_DEAD_AFTER_PING`. |
| Headers that fill memory | `neoteletext_http3::limits::MAX_FIELD_SECTION_BYTES` (16 KiB by RFC 9114 section 4.2.2's measure), refused on the HEADERS frame's length before any payload is held, and again as the section decodes, Huffman strings included; the same figure is HTTP/2's `MAX_HEADER_LIST_BYTES`. |
| A QPACK dynamic table that holds memory across requests, or blocks a stream on another | None exists: the server offers capacity 0 and no blocked streams, any reference to it is `QPACK_DECOMPRESSION_FAILED`, and the peer's encoder and decoder streams are read and dropped. |
| Frames that fill memory | Only HEADERS and SETTINGS payloads are held, within `MAX_FIELD_SECTION_BYTES` and `neoteletext_http3::limits::MAX_SETTINGS_BYTES` (512); DATA is passed on as it comes and unknown frames are passed over unheld. HTTP/2 frames are at most `H2_MAX_FRAME_BYTES`. What a QUIC peer may send before it is read is `QUIC_STREAM_WINDOW_BYTES` (32 KiB) a stream and `QUIC_CONNECTION_WINDOW_BYTES` (64 KiB) a connection, at most 3.7 GiB over every connection at the bound; what the server holds unacknowledged for a peer is `QUIC_SEND_WINDOW_BYTES` (256 KiB) a connection, in place of quinn's ten megabytes; QUIC datagrams are refused (REQ-7006). |
| Malformed HTTP/3 that crashes or stalls a reader | The engine's `neoteletext-http3` has the engine's no-panic lints, unit tests at and past each bound, and the engine's fuzz target `http3_reader`, run by the engine's full gate. A fault is the connection or stream error RFC 9114 section 8.1 names: frames of HTTP/2 and `PUSH_PROMISE`, a second control or QPACK stream, a client's push stream, a control stream that does not start with SETTINGS, reserved or repeated settings, and a malformed request (RFC 9114 sections 4.2 and 4.3.1), which ends its stream alone. |
| A web page reaching a channel as the viewer over the new openings | The checks are one function for every version of HTTP (`http::decide`): `Origin` is refused 403 and the subprotocol required over extended CONNECT as over the upgrade. |
| More WebSockets a peer than before | A WebSocket no longer costs its peer a TCP connection: one connection carries up to `MAX_CONCURRENT_STREAMS`. Each is a connection to the channel like any other, read by the same WebSocket reader within the same message bound, counted in the same figures, and its viewer bounded by address as before (VS-304), the address being the TCP or QUIC peer's as the connection was made. |
| The private key | Read once at start from the file named and never logged. Its file's permissions are the operator's. |

**The PROXY protocol header** (DEC-6972, REQ-6974; reviewed 20 November 2026, with the build). With `--proxy-protocol` the server reads bytes before TLS, and believes an address they state. The specification is HAProxy Technologies' "The PROXY protocol, Versions 1 & 2"; its section 5 names the first threat.

| Threat | Mitigation |
|---|---|
| A viewer sends a header and claims any address, escaping the bound on new viewers or spending another address's | The header is read only from connections whose peer is the one address `--trusted-proxy` names; any other peer's connection is closed with nothing read from it. The option is explicit and the server never guesses whether a header is there (the specification's sections 2 and 5): without it no header is read, with it a connection that starts with TLS is closed. What remains is the operator's: the listening port must be reachable only by the proxy, as REQ-6960 has it for production, since a process at the proxy's address can state any address. |
| A viewer behind the proxy names an address in `X-Forwarded-For` | Not read on TCP behind the PROXY protocol (`http::Source::Viewer`): the proxy relays the request encrypted and wrote none of it. This holds for the proxy's own LOCAL connections too. |
| A header that fills memory, or a length that makes the server read without end | The whole header is at most `MAX_PROXY_HEADER_BYTES` (536, the specification's 576 - 40), checked on the 16 fixed bytes before any of the rest is read, and read into one buffer of that size on the connection's task; nothing is allocated by a length the peer states. |
| A connection opened and left before its header, or a header sent a byte at a time | `PROXY_HEADER_WITHIN` (5 s) from the connection being accepted to its whole header, after which `HANDSHAKE_WITHIN` bounds TLS. Bytes that are not the signature are refused at the first wrong byte. **Open**, as above: TCP connections are not counted (TODO-6969), though here only the proxy's are read at all. |
| A malformed header that crashes the reader, or one read past its end into the TLS handshake | `proxy_protocol::read` has the workspace's no-panic lints, unit tests of every refusal and of every truncation, and the fuzz target `proxy_protocol_reader`, which also holds it to asking for no byte past the header's end. TLV vectors are skipped by the header's length alone and never interpreted. |
| An address family the server has no use for is taken as a viewer's | Only TCP over IPv4 and over IPv6 give an address; UDP, Unix sockets and the unspecified family are refused with a PROXY command. An IPv4-mapped IPv6 source is counted as its IPv4 address, so one viewer has one address. |
| A viewer's address in the log | The reason a connection was closed is logged at debug level without any address (REQ-1049). |
| `Alt-Svc` sends clients to a port that is not the server's | It names the origin's port, not the listening port (REQ-6965 version 2); behind a proxy that port is the proxy's, and whether QUIC is answered there is the proxy's configuration (DEC-6972 item 4). |

A client that has gone holds a stop for `STREAM_ACKNOWLEDGED_WITHIN` and `QUIC_CLOSED_WITHIN` at most (REQ-7002). The certificate and key are read again at `SIGHUP` (REQ-7003), and the deployment reloads the server when Caddy renews them, so no renewal closes a connection.
